# Architecture

## Modules and dependency direction

- **spooky-core** defines the bounded versioned wire protocol, own-user local IPC paths, and local/SSH client transport. It has no GUI or terminal-renderer dependency.
- **spooky-server** owns workspace layout, shell processes, PTYs, terminal emulation and agent processes (coding agents such as oh-my-pi, run without a terminal). It depends on spooky-core, portable-pty and alacritty_terminal.
- **spooky-desktop** builds the spooky executable. It owns presentation, keyboard focus, clipboard, screenshots and window integration. It depends on spooky-core and iced with its wgpu renderer.

The GUI never owns the lifetime of a shell. The server never needs a display server or GPU.

`spooky-server` and `spooky-core` follow the same rules:

```
spooky-server/src/
  main.rs      module list and the entry point (Unix only)
  cli.rs       serve, bridge, status, version and stop: argument dispatch and the control commands
  daemon.rs    the socket: single-instance lock, accept loop, one request per line, the save thread
  server.rs    Server: the shared state, request execution, save and restore, shutdown
  state.rs     State (workspaces, panes, identities), layout edits, and the validation of names, sizes and directories
  pane/        mod.rs (a pane: PTY, emulator, listener, snapshot), render.rs (rows and the row cache), shell.rs (the shell command)
  shim.rs      the omp shim: the script and zsh startup file written under the state directory, and the variables and PATH given to shells
  agent/       mod.rs (the Backend trait, normalized Event, the bounded Transcript, the child process and its reader), omp.rs (the oh-my-pi backend); see agent.md
  settings.rs  server.toml; persist.rs (saved workspaces); search.rs (scrollback matches); log.rs
spooky-core/src/
  lib.rs       the wire protocol
  paths.rs     the own-user socket and state directories
  client/      mod.rs (Client and Target), local.rs (Unix socket), ssh.rs (SSH child and its helpers),
               upload.rs (SFTP transfers), framing.rs (bounded JSON lines), errors.rs (Cancelled, Unrecoverable),
               install.rs (the server on a remote machine), fetch.rs (curl downloads, checksums, scratch directories)
  update.rs    the application's own update: release list and channels, check, prepare, apply, relaunch
```

Rules: a feature is a folder; features do not import one another (they meet in `App`, which composes them, and talk through messages and small traits `App` implements, such as `settings::Shortcuts`); the shared leaf modules (`config`, `ui`, `platform`) depend on no feature; tests live beside the code they test. A feature reports what the rest of the application must do as data (`settings::Effect`) instead of reaching into it, which is also what lets its logic be tested without a display. The same rules will apply to mods.

## Agent web view

On macOS `app/web.rs` drives one `WKWebView` (`platform/macos/webview.rs`, through `wry`) that is a child of the main window and shows the agent pane that fills its tab. Responsibilities: the native layout reserves the pane's area with a measuring canvas that reports its rectangle; the application places, shows and hides the view, and pushes `features/agent/web::state` (the server's `Agent` as JSON) when it changed. The page posts messages through a bounded channel; `features/agent/web::event` parses them into a closed set, bounds them, and maps them to the messages the native view sends, so the server and `omp` are reached only through the usual requests. A forwarded chord becomes a command only if `shortcuts::shortcut` knows it. The view is hidden while a native overlay is open, since a child view draws above iced; splits, other platforms and a failed start keep the native `features/agent/view`. The page (`web/agent`) is built to one HTML file, committed, with a Content-Security-Policy that allows no network, and navigation and new windows are refused. `platform/webview.rs` is the only place that knows whether the view exists. Dependency direction: `app` → `features/agent/web` and `platform/webview`; the page depends on nothing in Rust but the JSON shape of `spooky_core::Agent` and the action set.

## Transport

Local requests use a private Unix-domain socket in an owner-only directory. A client can start the sibling spooky-server executable, or an explicit SPOOKY_SERVER path. SPOOKY_SOCKET supports isolated environments and tests.

Remote requests use a persistent SSH child invoking spooky-server bridge. Bridge relays one bounded JSON-line request and response at a time to the remote user's local session server. SSH stderr is diagnostic; stdout is protocol only. The bridge/client may exit while the actual session server keeps running.

The two transports implement the same client interface. This is the seam for the optional remote module. Extensibility is a separate, planned design: see [mods](mods.md). Uploads use SFTP separately from terminal input. Standard OpenSSH configuration and known-host verification remain authoritative.

`spooky-desktop::tailscale` performs read-only discovery with the installed CLI (`TAILSCALE_BE_CLI=1` for macOS app binaries). Tokio runs the child off the GUI thread, bounds stdout/stderr and applies a ten-second deadline with kill-on-drop. Discovery projects only typed IP addresses into SSH destinations; device labels are display-only, self is excluded, and offline peers remain visible but disabled. The native picker prepares a destination; only the existing Connect action changes transport. It does not install, authenticate, reconfigure Tailscale or bypass OpenSSH host checks.

## State and rendering

The server parses PTY output through alacritty_terminal and produces viewport rows of styled runs with resolved colors, cursor and input modes. This permits a reconnecting client to recover state without replaying an unbounded output log. Workspace layout and terminal grids remain server-owned.

Tab and pane locks belong to the server's saved workspace tree, so all clients and reconnects see the same protection. New tabs and panes are unlocked. Explicit close requests are checked atomically against locks: a locked tab cannot be closed, a locked pane cannot be closed or removed via its tab or workspace, and a locked tab protects its last pane. Workspace closure still requires confirmation and cannot bypass locks. Closing the last unlocked tab or pane leaves an empty workspace rather than deleting it. Normal shell exit remains process-controlled and removes its pane and associated lock. Lock updates are explicit desired states, not toggles, so delayed clients cannot invert them accidentally.

Snapshots carry a server-scoped revision. Since protocol v3 a snapshot returns a complete workspace tree but only the panes changed since the requested revision, and within each pane only the rows that changed. `since: None` requests a full snapshot; clients reset the revision on reconnect or target change. The desktop merges updates with `Pane::apply_update` and removes panes absent from the authoritative tree. Layout changes send every remaining pane in full, including newly inserted panes whose initial output preceded insertion. A changed grid size also sends every row.

Protocol v18 adds per-shell PTY-output and per-agent completed-turn counters to pane snapshots. The PTY reader increments its counter while holding the terminal lock before publishing its revision; resizing, scrolling and rendering do not advance it. Agent turn completions are counted in the transcript so a turn that starts and finishes between snapshots is still observable. Pending dialogs retain their existing bounded identities.

The desktop derives unread markers per pane from merged snapshots, aggregates them by tab and acknowledges only panes actually viewed in the focused, visible window (respecting the settings page and zoomed splits). Current dialog identities track whether each question was seen; closing a dialog removes its pending marker. A client establishes a baseline for old output and turns on connection or reconnection rather than conflating reused server-scoped IDs, but still flags unseen pending dialogs. Acknowledgment is local to the client, not sent to the server; reconnecting can therefore discard unread output and completion markers. No additional CLI or operating-system notification is involved.

A viewport row is a `Line` of `Run`s: adjacent cells sharing one style, with blank cells on the default background left implicit. A run is one single-column cell per scalar value; a wide cell or one with combining characters is a run of its own (`Run::width`). A row that became blank is sent as an explicit empty line. Each server pane keeps a `RowCache` of its last rendered rows and the revision at which each changed. A snapshot renders under the terminal lock, reads the pane revision there (content and its revision bump are committed together under that lock), updates the cache, and returns the rows newer than the client's `since`. Clients at different revisions therefore each receive what they lack; a stale client can receive a row twice, never miss one. On the wire a mostly blank 300×80 screen is about 2 KB and one echoed keystroke about 0.5 KB, instead of the former 3 MB for either.

An up-to-date snapshot request waits on a condition variable until PTY output, exit, resize, scroll or layout changes advance the revision. A one-second idle heartbeat bounds the wait; it adds no delay to active updates. No terminal or workspace lock is held while waiting. The desktop uses separate command and snapshot connections (and separate SSH bridges remotely), so a waiting snapshot or its serialization cannot hold up keyboard input. Ordered deltas reach iced through a bounded asynchronous channel with backpressure; native global-shortcut callbacks share that wake-up path.

The link reports each connection's state to the frontend as `Event::Connection` (commands and display separately). These transitions use blocking sends so a full event queue cannot leave a stale "connected" indicator; the frontend shows connected only while both are up.

Connection attempts are cancellable. `Client::connect_cancellable` polls a caller predicate while waiting for the SSH handshake or local server start; on cancellation it kills the SSH child and returns `Cancelled`. `Link::retarget` queues the target change and then publishes the newest generation in an atomic, so an attempt for an older generation on either thread is abandoned instead of waited out, and the user can leave a hung host immediately. Failures are typed: `Unrecoverable` (rejected login, host-key failure, unknown host, missing `spooky-server`, protocol mismatch, missing `ssh`) stops automatic retries until the next target request; everything else retries with a doubling backoff from 2 s capped at 30 s. The command thread reports `Event::Unreachable` with a blocking send, since it is state, and the frontend shows the reason with Retry / Use this computer rather than an indefinite waiting pane. Dropping an SSH transport kills the child and waits at most 500 ms for its helper threads, so a pipe held open by a leftover process cannot stall the caller.

Both endpoints must negotiate protocol v18. There is no compatibility mode and no automatic server restart: replacing an existing server terminates its shells, so the user must finish those sessions before upgrading the running daemon (`spooky-server stop` exists from v6 on; older servers are ended by process).

Protocol v4 adds each pane's mouse state, taken from the emulator's mode flags: tracking (`Off`, `Clicks`, `Drag`, `Motion`; the most detailed enabled mode wins), encoding (`Normal`, `Utf8`, `Sgr`) and `alternate_scroll` (alternate screen with DECSET 1007 on). It also adds `Cursor::shape` and `Run::strikethrough`. The server runs the emulator with a steady-bar default cursor so shells that never send DECSCUSR look as before, and applies the dim attribute by scaling the foreground to two thirds (the foreground is dimmed before reverse video swaps it).

Protocol v5 added `RenameTab` and `CloseTab`. Tab titles and membership are server state like workspace names, so every client sees a rename and a closure; `CloseTab` removes the tab and all its panes in one step under the state lock, then terminates the shells after the lock is released. Originally closing the last tab removed its workspace; v17 retains the empty workspace until explicitly deleted.

Protocol v6 moves more terminal state to the server and adds the operations that need it. Layouts carry a split `id` and a `ratio` (the first side's share in thousandths, kept within `MIN_SPLIT_SHARE`), and `SetSplitRatio` moves a divider, so divider positions are shared by every client and saved with the layout. Tabs carry `renamed`; an unnamed tab is labelled with its terminal's title (`Pane::title`, cleaned and bounded by the server). `Run::link` carries an OSC 8 target, bounded and free of control characters. `Cursor::blinking` and `Pane::focus_reporting` expose DECSCUSR blinking and DECSET 1004. `Pane::history` and `scrolled` describe the scrollback position. `Find` searches a pane's whole scrollback with the terminal lock held for at most `SEARCH_LINES` lines; the server remembers the query and the last match per pane, answers `Found` or `NotFound`, scrolls the viewport to the match, and reports the matches inside the viewport as `Pane::highlights`, recomputed from the visible rows on every snapshot so scrolling keeps them right. OSC 52 writes are kept per pane (latest only, at most `MAX_CLIPBOARD_BYTES`); the pane advertises a counter, and a client that sees it grow fetches the text with `Clipboard`, so each client acts on a write once and a large payload is never repeated in snapshots. Reading the clipboard stays refused by the emulator configuration. `Status` and `Shutdown` serve `spooky-server status` and `stop`.

Translating pointer events into bytes belongs to the frontend (`pointer`, used by the terminal canvas). While tracking is on, the pane is not exited and Shift is not held, presses, releases, motion and wheel notches become reports sent as ordinary pane input, and the pointer no longer selects text or scrolls history; Shift restores both. iced mouse events carry no modifiers, so the canvas follows them from keyboard events. Motion is reported only when the pointer enters another cell, only with a button held in `Drag` mode, and a drag that leaves the pane keeps reporting at the nearest edge cell until release. The release of a reported press is still reported if Shift is pressed in between. Legacy encodings drop positions they cannot express rather than clamping them. A wheel event forwards at most 30 notches, and with tracking off on the alternate screen the wheel becomes arrow keys honoring application cursor mode.

The frontend draws each row run by run through iced's GPU-backed canvas/text infrastructure: one background rectangle per non-default run, a selection rectangle per row, and one glyph per non-blank cell so the grid stays aligned when fonts fall back. iced already incorporates text layout/rendering crates; adding a second independent renderer is not required merely to name cosmic-text or glyphon as direct dependencies.

`spooky-desktop::view` composes a compact unified header, flat workspace navigation, floating action menu and confirmation overlays; `chrome` holds shared visual tokens and vector icons. Pane titles are omitted to preserve terminal space and panes have no border of their own; status and exited state appear in the header. The header's folder control exposes the directory popover, while the invisible bottom-edge grip still resizes the window. The default terminal background is shared through spooky-core so server-resolved cells and frontend padding match. Indexed and truecolor backgrounds remain distinct from that default.

On macOS the desktop composes a native behind-window material beneath a translucent
dark backing. The configured opacity affects that backing, not the window alpha,
so text and controls stay opaque and the dropdown fade remains independent. The
system's Reduce Transparency setting and 100% opacity use a solid background.
The terminal protocol carries whether a background was explicitly selected, so
even an explicit color equal to the default remains opaque; older servers do not
provide that distinction. The agent web view exposes the same backing instead of
painting an opaque page. Other platforms keep their existing solid background.

Machine disclosure, sidebar visibility and the SSH editor have independent UI state. The machine name and chevron toggle only its workspace list, preserving the active pane and transport; the chevron reflects that state. A separate + button on the same machine row creates a workspace on that target without toggling the disclosure. Creating a workspace or switching targets expands the list. Only Connect machine opens the SSH editor. Escape or hiding the sidebar dismisses that editor rather than leaving terminal input disabled by an invisible field.

Workspace context actions retain the clicked workspace ID independently of active selection. Rename and close dialogs use that ID, not whichever terminal is active; snapshot reconciliation and target changes clear stale action state. Destructive confirmation displays the target name. Modal input is isolated from the PTY, and action menus dismiss on Escape or outside clicks.

Workspace, tab and pane context menus share one overlay, `App::context_menu: Option<(ContextTarget, Point)>`, so Escape, outside clicks and the keyboard guards treat them alike, and `reconcile` closes the menu when its target leaves the snapshot. Right-clicks reach it from a transparent `RightClick` canvas over a workspace or tab, or from the terminal canvas when the program is not tracking the mouse (Shift takes it back). Opening a pane menu selects that pane. Buttons and menus send targeted messages; pane and tab closure respects server-side locks without confirmation. A tab's double click is deliberately not bound: on macOS a double click inside the unified titlebar area zooms the window.

`spooky-desktop::shortcuts` is the table of application chords: a pure function from key, physical key and modifiers to a command, which `App::run_command` turns into the message the corresponding button sends. It is consulted for ignored key events while the terminal owns the keyboard, except Quit and the search chords in their field. A split agent's native composer handles the pane zoom chord directly without sending or editing its draft. macOS chords use Cmd; other platforms use Ctrl+Shift, so plain Ctrl stays terminal input. Digits and brackets are matched by physical key so they are layout-independent, and Cmd+Shift+digit is left to the system screenshot shortcuts. Pane and tab closure is immediate when unlocked; workspace closure still confirms.

The dropdown window state is tracked from real events, not toggled blindly. `hidden` records that Spooky itself hid the window; `focused` follows the window's focus events. The global shortcut hides a shown, focused window. With stay-on-top enabled, it also hides an unfocused window when the native minimized-state query confirms it is not minimized; on macOS the uniquely identified window must also be visible on the active Space and the application not hidden. When the query is unavailable (including Wayland), focus remains the conservative fallback. Otherwise the shortcut reveals the window (un-hides, un-minimizes, focuses). Shortcut presses arriving during the asynchronous query are coalesced by parity; a generation rejects superseded responses, and hiding or revealing cancels the pending decision. The close button hides only while a global shortcut is registered; without one it quits, because a hidden window with no way back would strand the application. On macOS `macos_app::set_dock_icon` sets the process's activation policy at window open and when the setting changes (accessory unless `dock_icon = true`, and always regular without a global shortcut). `on_blur` uses the same focus events and does not hide for Spooky's own file dialogs.

On macOS, a reveal selects the `NSScreen` containing the pointer and converts its AppKit frame into global top-left coordinates. Percentage dimensions use that screen's usable size; pixel dimensions remain fixed. Safe AppKit placement sets the frame in the destination's logical coordinates, avoiding iced's conversion using the old display's scale during a mixed-DPI move. The window is placed before showing on a different display; a same-display reopen starts the slide and requests visibility and focus immediately. A close in progress reverses from its current position. Starting a close does not clear `focused`: the native focus event remains authoritative. Reveal generations discard measurements superseded by another reveal or hide.

The dropdown starts hidden whenever the global shortcut is registered. `Opened` disables macOS's native window animation before the first reveal, and duplicate open notifications are ignored. If native pointer-display placement is unavailable, the existing iced placement path remains the fallback. Other platforms retain their existing display selection.

`spooky-desktop::config` owns `config.toml`: the typed `Config` (unknown keys and out-of-range values are errors), loading, and `save`, which writes the whole file through a temporary file and a rename. The settings page (`settings.rs`, drawn by `App::settings_page` in place of the terminal while `App::settings` is set) only emits `Change` messages. `App::change_setting` builds the next `Config`, and `apply_config` validates and saves it and then updates what each changed field drives: a font-size change refits every pane's grid (`refit_grids`, the same `fit` the bounds message uses, so the server learns the new size); a size change marks `size_pending` and reveals, so `Present` resizes the window against the display's usable area; `on_blur` sets the window level; the Dock switch sets the activation policy. A failed save leaves the change applied and says so in the page header. A plain reveal on the same display keeps a resized window's size; changing displays recomputes percentage dimensions. The shortcut recorder consumes key presses while `recording`: `shortcuts::hotkey_text` turns one into a chord the `global-hotkey` parser accepts (a function key alone, otherwise Ctrl, Alt or Cmd is required so no typing key is taken from other applications), and `register_shortcut` registers the new chord before unregistering the old one, so a refusal keeps the working shortcut. `App` owns the `GlobalHotKeyManager` for this reason. The Settings page is a tab of its own, local to the GUI and not a server tab: it is listed after the workspace's tabs while `Settings::is_open`, is the selected one while `is_shown`, and choosing another tab or workspace only hides it. `terminal::TerminalFont` holds the configured family and the advance of its cells, measured through iced's font system (`terminal/font.rs`), because the grid the server is asked for is the area divided by the cell size; changing family or size refits every pane.

Uploads (`spooky_core::client::upload`) never run on the command thread. The link starts a transfer on a dedicated thread (one at a time) whose cancellation predicate is the same newest-generation atomic as connections, and reports the result as an event. For SSH one round trip sweeps upload directories older than seven days, prints `$HOME` and creates a private `~/.spooky-upload.XXXXXX`; the reported directory is validated (absolute, inside the reported home, alphanumeric suffix) before any path derived from it is used, `sftp` copies the file in batch mode, and a failed or cancelled transfer removes the directory (a shell-quoted `rm -rf` of the validated path, with its own short timeout). The transfer timeout is 30 s plus the file size at 256 KiB/s, capped at 30 minutes, so a large file on a slow link is not cut off by the limit meant for a stalled one.

`ui::themes` discovers bounded, data-only TOML themes alongside `config.toml`
at startup and retains diagnostic messages for Settings. `Config::appearance`
preserves the original built-in choice, while `custom_theme` stores the selected
additional theme's ID. If its file disappears, the built-in choice is used until
the file returns. The iced palette drives native surfaces and is forwarded to the
bundled agent page; terminal cells inherit its background only when the server
reports the default background. Explicit terminal colors remain server-owned,
with no protocol or CLI change.

Terminal panes and the draggable `divider::Divider` share the window's background. The divider leaves its six-pixel hit area transparent and paints a single line, highlighted while hovered or dragged. A passive scrollback indicator occupies the outer edge of a scrolled pane, outside the terminal's text padding; its tooltip reports the scroll position.

Keyboard events retain iced's captured/ignored status and physical key identity. Only ignored input reaches the terminal; Escape can dismiss an overlay even when a text field captured it, without forwarding that event to the shell. Space preserves its OS-provided text, including a composed character, while Control+Space emits NUL. On macOS, `macos_keyboard` resolves Option dead keys through AppKit's layout-aware `charactersByApplyingModifiers` API using safe `objc2` crate interfaces. It reuses winit's physical-key mapping, commits the spacing glyph immediately and discards that native composition session so the next key is not duplicated or accented. Other text keeps OS composition; no Spanish-specific character table is maintained. Option-generated text has no Meta prefix; Control+Option chords and printable Alt input on other platforms retain the terminal escape prefix.

Clipboard chords are resolved by `clipboard_action`: Cmd+C/V and Ctrl+Shift+C/V, never plain Ctrl+C/V. Bracketed paste removes ESC and ETX from the pasted text (`paste_bytes`) so clipboard contents, which are untrusted, cannot terminate the bracket and run the remainder as typed input. Selection text drops the blank cells that pad each row.

Terminal clear and copy-all are server operations: the emulator owns both the viewport and scrollback, including for SSH clients. Clear removes both the viewport and scrollback without writing bytes to the PTY, moves the active cursor line and its wrapped rows to the top while retaining the cursor's position within them, and refuses the alternate screen rather than disturbing full-screen programs. Cleared output cannot be recovered by scrolling or copying. Copy-all reads the retained normal or alternate grid as a bounded snapshot, preserving line wrapping and Unicode while excluding concealed cells; it refuses oversized exports rather than returning partial text. The desktop owns the all-selection highlight and clipboard, and fetches the snapshot on a separate connection with cancellable setup so a slow SSH transfer cannot block input. Results for an obsolete target or pane are discarded; a failed or cancelled copy never changes the clipboard. Protocol v16 carries these operations and requires matching local and remote servers.

A divider drag publishes the pointer's window position. `App::split_geometry` takes the split's area as the union of its panes' reported bounds grown by the pane padding, and `divider::ratio_at` turns the position into a ratio (the divider's own thickness is not shared). The dragged ratio is drawn immediately and sent to the server at most every 40 ms and once more at release; it is dropped when the server shows the same ratio or has had a second to. Sides are sized with `FillPortion` from the layout's ratio, so the server's value and the drawn one use the same arithmetic.

Pane zoom is a desktop-only presentation choice scoped to the selected tab and pane. The renderer borrows the selected leaf of the server-owned layout without mutating that tree; other panes continue running. Leaving the selection or losing the split clears zoom. Normal bounds reporting resizes the enlarged PTY and resizes it back on restoration, so other clients observing the same pane also see that terminal size. A split agent uses the native agent view while enlarged, with its composer retaining the zoom shortcut and focus. No protocol or CLI change is needed.

`links` finds the link under a cell: an OSC 8 target (adjacent runs with one target are one link) or a plain `http(s)://` URL (bounded by blank columns and quoting characters, without sentence punctuation or brackets the URL does not open). It is consulted only while the link modifier is held, and `links::open` runs the system opener for the `http`, `https` and `mailto` schemes only; the target is shown in the header first because an OSC 8 target need not match its text. OSC 52 text arrives as an event and is written to the clipboard only when `osc52` is `write`; the per-pane write counter is baselined the first time a pane is seen so a reconnecting client does not replay old writes. A blinking cursor drives a 530 ms subscription only while the window and pane have the keyboard focus, and typing makes it solid. `App::sync_focus_report` compares the pane that should hold the keyboard focus (window focused, terminal focused, pane selected) with the last one told, and sends focus-out and focus-in only to panes whose program asked for them; it runs after every message.

Search keeps its state in the frontend (`Search`: query, the pane it ran in, the last answer); the server owns the match position. The search chords are accepted while the search field has the keyboard, but iced's text field inserts the letter of Cmd+F and Cmd+G, so an edit that adds exactly that letter while the chord modifier is held is discarded (`is_chord_echo`).

## Machines

`features/machines` owns the list of machines, each machine's state (connecting, ready with a workspace summary, failed with an optional `Problem`) and the installation dialog; it is pure state. `probe.rs` runs the threads: one probe per machine that is not in use (its own client connection, a snapshot every 3 s, backoff 2–30 s, no retry for errors only the person can fix) and the installation and remote restart, which report through one unbounded event channel. `App` keeps a single `Link` for the machine in use, so a failing remote never affects it; `sync_probes` stops the probe of the machine in use and starts the others. The installer lives in `spooky-core::client::install` and runs only after the in-app confirmation; it never changes the remote's SSH configuration, never disables host-key checks and never restarts a server without a second confirmation. Showing several machines' terminals at once would need per-machine session state in `App` and is not done.

## Releases and updates

`spooky-core::update` owns the logic and has no GUI: `check` reads a release list (GitHub's JSON, or `SPOOKY_RELEASE_INDEX`) and applies the channel (Stable skips pre-releases and drafts; Dev takes the newest of every release; semver ordering, never a downgrade), `support` decides whether this installation may replace itself, and `prepare` / `apply` / `relaunch` do the update in three steps so nothing changes before the person agrees. Downloading, checksum and scratch-directory helpers live in `client::fetch`, shared with the remote installer. `prepare` unpacks beside the installation (same filesystem, so the swap is a rename), verifies the macOS bundle with `codesign --verify --strict`, and runs the new `spooky-server version` (one line: `spooky-server <version> protocol <n>`, defined once by `update::version_line`), which must name the expected version and gives the protocol the new server speaks. `apply` renames the installed files into a backup directory and the new ones into place, moving everything back if a step fails; dropping a `Prepared` removes the unpacked files. Only an installation a release made is replaceable (a `.app` bundle, or `bin/spooky` beside the release's desktop file) and only where a file can be created now; a package-manager install or a development build gets an explanation and the release page. There is no atomic bundle exchange without unsafe code, so the swap is two renames with rollback.

The desktop keeps `features/updates` as pure state (status, the dialog stages; the answer of a check for a channel that was left is ignored) and `updater.rs` runs the threads, reporting through one unbounded event channel like `probe.rs`; the prepared release waits in a slot until **Restart**. The update dialog is the only path that stops the local server, and only when the new protocol differs (`PROTOCOL_VERSION`): `prepare` then asks the running server how many shells and agents it holds (a failure to ask stops the update before anything changes), the dialog states that number, and `Updater::apply` replaces the installation first and stops the server second, so a server that does not stop leaves the old one running with a clear message rather than ending shells for an update that did not happen. The window exits after the new application is started detached with a one-second delay.

The release workflow's tag guard requires the tag to equal the workspace version; a version with a pre-release part (`0.2.0-dev.1`) publishes a GitHub pre-release, any other must be a commit of `main`. Asset names are the contract between the workflow and `update.rs` / `install.rs`.

## Process and failure behavior

PTY output, writes and child reaping must not block the shared workspace state. Input queues and wire frames are bounded. Closing the GUI is a detach. Explicit close requests remove the process and corresponding layout. For a normally exited shell, a server-owned reaper removes only its pane and empty tab; a covered agent remains, and a workspace may have zero tabs. That state is persisted and rendered with a New tab action. Exit notification and layout insertion both wake the reaper, so a short-lived shell cannot exit before registration and be missed. Process signaling and dropped pane cleanup happen outside the shared state lock. Shells killed by a signal or whose status cannot be read retain their viewport for diagnosis. Protocol v14 advertises the empty-workspace contract to clients.

The desktop explicitly requests the local user's home directory when creating local workspaces, independently of Finder's or the server's working directory. Remote requests leave the directory unset so the remote server resolves its own context. New tabs and splits use the selected source pane's verified directory; an agent created by the ordinary action still uses the workspace's starting directory. An empty workspace has no source and starts its new tab in its own directory. Existing shells are not relocated.

Tab and split actions and the separate “new agent here” action send the source pane identity, not a path supplied by the GUI. The server verifies that the source belongs to the requested workspace, releases the workspace lock, and reads the local shell process's current directory with `sysinfo`; an agent supplies its own starting directory. The PTY foreground process group must be the shell, and the server checks the shell executable and its children to reject a nested foreground program rather than mistake an SSH session's remote directory for a local one. Unsupported, exited or unreadable shells return an error, never a guessed path. The directory is validated before spawning. Each remote server performs these checks on its own machine; terminal output cannot set the directory. Process inspection is inherently a snapshot and can race process state changes, so the foreground group is checked again before use.

The command connection returns a failed creation's original request with its error to the desktop, without changing the wire protocol. The frontend can then offer a deliberate retry in the original workspace directory, never an automatic fallback: it displays the actual error, retains the original target, checks that target still exists and discards the offer on disconnect or target change. Other errors do not acquire a retry target, and a transport failure never replays an uncertain request.

Protocol v15 adds a read-only directory query for a pane. The server selects an agent's starting directory or inspects the original shell with the same foreground-process checks used by creation, outside the workspace lock; an unavailable or unsafe directory is an error, never a cached guess. A dedicated client connection periodically checks only the selected pane, coalescing selection changes, so a slow process inspection or SSH connection cannot hold up input or display snapshots. Selection changes, including a shell becoming an agent, carry a new token; responses from older targets, panes or tokens are ignored. A displayed shell path is a recent observation, not an instantaneous guarantee: it expires after a short timeout and becomes unknown on any failure or disconnect. The agent path is explicitly labelled as its starting directory. Nested SSH is not treated as a remote Spooky workspace.

The directory popover is GUI-only. It captures the selected observation's token and exact path, escapes control and bidi characters for display, and closes when the observation changes or expires. Copy rechecks that token and writes the exact path, not the escaped label. Opening a folder is offered only for a local connection and rechecks the same observation; filesystem inspection and the platform opener run off the GUI thread. SSH paths are labelled with their connected host and are never passed to the local opener. No protocol or CLI change is involved.

Each shell pane keeps its last verified local shell directory. A server worker checks panes whose terminal output changed at most once per two seconds; the final synchronous save checks them again. Inspection reads the original shell process's executable and working directory from the operating system, never terminal output. Foreground programs do not change which process is inspected: in particular a nested SSH session does not make the local server claim a remote directory. An exited, replaced, unreadable or invalid shell leaves its last verified value intact. The worker copies pane handles under the workspace lock, then performs process and filesystem work without that lock; only a changed directory marks the layout saver. The saved pane-to-directory map is optional for older files, validated against terminal pane identities, and restored independently on the owning server. A missing or inaccessible saved directory falls back to that workspace's restored starting directory and is logged. Checkpoints are best effort after an abrupt server or OS failure; output and processes are not persisted.

The server builds each shell with `shell_command`. macOS uses `portable-pty`'s default program, a login shell (`argv[0]` prefixed with `-`) resolved from `$SHELL` or the password database, because a Finder launch gives the server a minimal launchd environment without the user's profile or locale; it supplies `LANG=en_US.UTF-8` only when `LANG` and `LC_ALL` are both unset. Other platforms keep the plain `$SHELL` invocation until verified on real Linux desktops. `Request::Input` returns the pane's viewport to live output before the request completes, because the display offset belongs to the server-side terminal state shared by every client.

A dead remote SSH connection does not imply a dead shell. Failed commands and uploads are reported; input and destructive actions must not be retried blindly across disconnection or target changes.

The server writes `server.log` and `workspaces.json` in `spooky_core::paths::state_dir` (the socket's own directory under SPOOKY_SOCKET, so an isolated instance never touches real state). The log (`log` module) is private, capped at 1 MiB with one previous generation, and control characters are replaced so text from a client or terminal cannot forge lines. The layout is saved by a thread that waits for a change mark, lets a burst settle for 300 ms and writes atomically with mode 0600 (`persist`); `Shutdown` saves synchronously, terminates every shell, removes the socket and exits after answering. At start the file is read before the socket is bound: identities must be unique and issued, ratios are clamped, and a file that fails any check is moved aside as `.corrupt` and reported, never half restored. Restored panes are new shells using their saved directories when available, or their workspace's directory otherwise, at the saved window-sized grid, under the saved identities; identity allocation continues past every saved identity. The workspace directory itself falls back to home if unavailable. New panes outside a split start at the size of the largest existing pane. The scrollback limit comes from `spooky/server.toml` on the machine the server runs on. `spooky-server stop` refuses while shells run unless forced, because stopping ends them.

## Platform decisions

macOS and Linux use Unix sockets and native PTYs. Window shortcuts and placement are frontend concerns, separate from sessions. Wayland compositors may restrict global shortcuts and window placement. `platform/desktop.rs` decides the session once (`Session`: X11, KDE Wayland, other Wayland, native) and so `WindowControl` (the application through the windowing library, KWin, or nobody); nothing else reads the environment. A dropdown (`App::dropdown`) is a global shortcut plus a desktop that lets the window be hidden: on other Wayland the portal shortcut still registers but only raises an ordinary window, and closing quits. On KDE Wayland `platform/kwin.rs` and `platform/portal.rs` supply both: the shortcut through the GlobalShortcuts portal (`Hotkeys::Portal`; KDE owns the binding, so `rebind` is refused) and window placement, size, hide (the application slides its content out of the window, `features/window/slide.rs`, and KWin fades and parks it off screen; never minimized, since KWin's minimize effect flies the window to the task bar), raise and focus through a one-shot KWin script loaded over D-Bus on a worker thread, matched by process id and `dev.spooky.terminal` window class. Sizes given as a share of the display are resolved by KWin, because winit knows no monitor before the window is mapped; the first reveal waits 300 ms for the window to exist.

Windows is deferred rather than hidden behind WSL. Future Windows work includes local IPC, process-lifetime verification with ConPTY and native window integration. portable-pty is retained to avoid coupling the session model to Unix PTY syscalls.

## Security

Use safe crate interfaces; first-party unsafe is forbidden. Reject foreign/symlinked IPC paths. SSH must verify host identity. Remote output and titles are untrusted display data. File transfer and shell input are separate operations; a path is quoted and never automatically executed. No global network listener is required for local sessions.
